# ImageBatch v1.1.0 设计说明

## 模块与数据流

```text
Qt 窗口（主线程）
  ├─ QtConcurrent 预览（最多一个进行中，旧请求结果可被忽略）
  └─ BatchWorker（QThread 协调线程）
       └─ runBatch
            ├─ 固定 ThreadPool + 有界 FIFO 队列
            ├─ ResourceBudget：解码前估算并申请额度
            └─ processFile：读图 → 方向/颜色 → 缩放 → 水印 → 编码 → 保存
       ← 任务开始 / 完成 / 进度信号 → 窗口更新
       → 按输入顺序生成 CSV + JSON
```

`threadpool`、`resourcebudget` 只依赖 C++17 标准库。`processor` 负责单图和文件保护；`batchengine` 组合调度与图像处理；`batchworker` 桥接 Qt 信号；`mainwindow` 管理界面和预览。基准程序与桌面程序调用同一个 `runBatch`。

## 线程池与对象生命周期

池中固定数量的 `std::thread` 从队列取任务。队列容量限制等待的任务数；队列满时提交者通过条件变量等待，工作线程取走任务后通知提交者。提交发生在协调线程，因此等待不会冻结窗口。条件变量使用谓词处理虚假唤醒，队列、停止状态和统计值均由同一个互斥锁保护。

`submit` 将任务包装为 `packaged_task` 并返回 `future`，支持可移动但不可复制的捕获对象，任务异常经 future 传递。析构将停止标记设为真，唤醒等待者，处理完已接受的任务后 join 全部线程。线程池的拥有者必须保证析构开始时没有外部调用者继续提交；不支持在任务内部递归提交后等待同一池中的子任务。

批处理结果以互斥锁保护，进度通知串行发出，结果仍按输入下标保存。同一路径可出现多次，因此以任务下标标识界面行。回调异常被捕获并计数，不阻断其他图片。回调应尽快返回，不能反向等待引擎结束。

所有 future 收集后销毁线程池并 join，再读取结果和销毁预算对象，确保任务捕获的引用仍有效。后台线程通过排队信号通知 Qt 窗口，不直接修改控件。

## 预算控制与统计范围

读取图片头部尺寸后，按以下公式估算每张图片占用：

`输入像素数 × 12 + 输出像素数 × 8 + 8 MiB`

这近似表示三个 RGBA 输入缓冲区、两个输出缓冲区和工作空间。总预留量不得超过预算；不足时工作线程等待，取消时退出等待。单图需求超过整个预算时直接失败，避免永久等待。可移动的 RAII `Lease` 在正常返回、异常或移动赋值时归还额度。

这是保守的调度估计，不能保证编码库内部实现、字体缓存、界面、预览、线程栈及分配器的实际总内存。因此界面明确标注“估算缓冲区预算”，不是操作系统内存限制。单图解码另外使用 Qt 的 256 MiB 分配限制。

JSON 的 `peak_reserved_bytes` 是估算额度峰值；`peak_active_workers` 是已取出任务的工作线程峰值，包含等待预算的线程；`peak_queued` 仅包括仍在队列里的任务。单图耗时覆盖图像处理与保存，不含排队及预算等待。汇总 `elapsed_ms` 截止报告写入前；基准 `wall_ms` 计时整个 runBatch，包括报告写入。

## 取消、错误与输出保护

取消使用共享 `atomic_bool`。提交前、任务启动前、等待预算时检查它；已进入图像解码和编码的任务继续完成。不会强制中断 Qt 编码库；关闭窗口时也等待当前任务安全收尾。取消后的每个未处理项仍进入报告。

单图损坏、解码失败、超预算、输出失败或异常只使该项失败。输出先编码到同目录的独立临时文件并销毁 QTemporaryFile 关闭底层句柄，Windows 使用 MoveFileW 发布；目标已存在时失败，追加编号重试。临时路径由 scope guard 清理。非 Windows 分支使用排他创建硬链接，桌面程序尚未在该平台验收。

不能只依靠“先检查文件是否存在”，真正发布时仍要禁止覆盖。初次 Windows CI 发现 16 个并发任务只有 13 个不同输出路径，本地重复运行也复现。审查固定 Qt 版本源码后发现：QTemporaryFile 首次重命名失败关闭底层句柄，后续可能转入 QFile::rename；其失败回退含有截断目标文件的复制流程。因此移除了该重试路径，直接使用不覆盖目标的原生接口。回归测试增加不同内容的同名图片、保留已有文件和跨轮次哈希检查。参考 [Qt 6.8.3 临时文件实现](https://github.com/qt/qtbase/blob/v6.8.3/src/corelib/io/qtemporaryfile.cpp)、[QFile 实现](https://github.com/qt/qtbase/blob/v6.8.3/src/corelib/io/qfile.cpp) 及 [MoveFileW 文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefilew)。输入与输出目录分开，处理前后测试原图哈希。

CSV 包含每个输入的最终状态；同名 JSON 记录总体耗时、成功/失败/取消数和调度指标。报告保存失败会在最终界面提示，已经保存的图片仍保留。

## 性能与取舍

线程池提高多张图片的处理吞吐量，队列背压限制待调度工作项；预算减少多张大图同时解码的风险。图片列表、future 和结果仍按文件数保存，整体元数据为 O(N)，有界队列不意味着整个程序内存为常数。

Windows 重复基准曾发现并行文字绘制产生极少量字形像素差异。当前仅对短暂的字体测量与文字绘制加互斥锁，解码、缩放和编码继续并行；修复后 9 次正式测量的全部输出哈希相同。这是基于观测的规避措施，未把底层字体实现认定为已证实的根因。Qt 全局辅助线程池固定为 1，避免多个图片任务嵌套扩张辅助线程。

基准使用固定合成语料、独立进程、轮换线程数顺序、一次不计时预热和每组 3 次测量，保留原始记录。输出哈希校验在计时之外执行。更多线程不保证加速：编码、存储带宽、预算等待和文字临界区均可能成为瓶颈。Linux CI 只验证标准 C++ 运行时，不代表 Qt 桌面程序已在 Linux 验收。
